You are a senior full-stack developer, UI/UX designer, database architect, and product engineer. Build a polished, functional, multi-college academic platform called CampusMate.

PRODUCT VISION CampusMate brings college announcements, teacher-shared notes, assignments, practical submissions, deadlines, timetables, academic calendars, and student self-study planning into one organized platform. It must be designed for multiple colleges, not one specific institution.

TARGET USERS

  1. Students
  2. Teachers
  3. College administrators
FIRST: BUILD A FUNCTIONAL MVP

Prioritize working features, a professional design, and a reliable demo. Do not build every advanced feature before the core works. Do not merely generate a static mockup.

TECHNOLOGY Use a modern responsive web stack supported by this coding environment. Prefer React with TypeScript and a clean component structure if supported. Use a real database and authentication service if available and practical. If credentials or services are unavailable, build a clearly labelled demo mode with sample data and explain how to configure production services. Never invent a successful connection to a backend. Never hardcode secret keys.

DESIGN Create a premium, modern student-productivity interface. Use a clean navy/blue and white theme with a subtle accent colour, readable typography, clear cards, generous spacing, consistent icons, responsive layouts, accessible forms, and helpful empty states. Desktop should have a sidebar; mobile should have compact navigation. Avoid excessive gradients, clutter, and generic landing-page-only designs.

  1. MULTI-COLLEGE ONBOARDING
  • Create a welcome page explaining CampusMate.
  • Allow a user to select a college from a searchable college directory.
  • Allow an authorized administrator to register and manage a college.
  • Collect the user's role, course/branch, academic year, semester, class/division, and relevant subjects.
  • Support a college-issued joining code or administrator approval for student enrollment.
  • Teacher accounts must require verification or approval by an authorized college administrator before they can publish official announcements.
  • A college name entered by a user must not automatically count as a verified institution.
  • Keep each college's users, courses, classes, files, announcements, and academic records logically isolated.
  1. AUTHENTICATION AND ROLES Create separate Student, Teacher, and College Administrator experiences.
  • Use secure authentication when a supported backend is configured.
  • Enforce permissions on the server/database, not just by hiding UI elements.
  • Students can view content for their enrolled college and classes.
  • Teachers can publish content only to authorized classes and subjects.
  • Administrators can manage their own institution and approve teachers.
  • Provide a clearly labelled demo mode with fictional users and sample data when real authentication is not configured.
  • Never claim demo accounts provide production-grade security.
  1. STUDENT DASHBOARD
Display:
  • One unified feed for relevant announcements from all subjects.
  • Upcoming assignment and practical deadlines.
  • Overdue and completed tasks.
  • Recently shared notes.
  • Today's timetable.
  • Upcoming college events and holidays.
  • A personal self-study plan and progress overview.
  • Filters for subject, announcement type, date, and unread status.
  • Search across accessible announcements and notes.
  1. TEACHER DASHBOARD Allow verified teachers to:
  • Select an authorized subject, semester, class, or division.
  • Create, edit, and archive announcements.
  • Mark genuinely important announcements as important.
  • Upload notes or attach supported documents after a topic is completed.
  • Include subject, unit, topic, description, and publication date with notes.
  • Create assignments and practical submissions with instructions, issue date, deadline, and attachment.
  • Edit deadlines and visibly identify updated deadlines.
  • Publish timetable changes and class notices.
  • View a list of their published items.
  • Clearly identify the audience before publishing.
  • Avoid sending announcements to unrelated colleges or classes.
  1. UNIFIED ANNOUNCEMENTS FEED
  • Show all relevant subject and class announcements in one place.
  • Include title, teacher, subject, class, date, type, and importance.
  • Provide filters, search, unread/read status, and sorting.
  • Open the full announcement and its attachments.
  • Display deadline changes clearly.
  • Support in-app notifications when feasible.
  • Do not claim push notifications or email delivery unless actually configured and tested.
  1. NOTES LIBRARY
  • Organize notes by college, course, semester, subject, unit, and topic.
  • Let authorized teachers upload notes and link them to completed topics.
  • Let students access and download permitted materials.
  • Allow students to bookmark notes and save personal resource links.
  • Support PDF attachments if the configured storage service supports them.
  • Validate file types and enforce file size limits.
  • Protect private materials using appropriate permissions.
  • Do not fabricate uploaded files or pretend that a link works without testing it.
  1. ASSIGNMENT AND PRACTICAL TRACKER
  • Allow teachers to create assignments and practical tasks with clear deadlines.
  • Display all relevant tasks on the student dashboard.
  • Let students track personal progress: Not Started, In Progress, and Completed.
  • Show due soon, overdue, and completed sections.
  • Allow filtering by subject, task type, and date.
  • Support student file submission only if actual storage and submission functionality is configured.
  • Clearly distinguish marking a personal task completed from officially submitting work to a teacher.
  1. SELF-STUDY PLANNER
  • Let students add topics, subjects, available study time, duration, and priority.
  • Generate a simple daily plan using task deadlines, urgency, and available time.
  • Reserve time for revision instead of allocating every minute to assignments.
  • Let users edit and complete study sessions.
  • Explain that scheduling is rule-based unless a genuine AI service is configured.
  • Never promise that an automatically generated plan guarantees academic success.
  1. TIMETABLE AND ACADEMIC CALENDAR
  • Create a weekly timetable with days, time slots, subjects, rooms, and teacher names where available.
  • Display upcoming exams, practicals, assignment deadlines, college events, holidays, and academic dates.
  • Allow authorized administrators to publish official timetables and calendars.
  • Let authorized teachers publish permitted class-specific timetable changes.
  • Make timezone and date formatting consistent.
  • Clearly label demo schedules and sample dates.
  • Do not present fictional timetable data as a real college schedule.
  1. NOTES REQUESTS AND CLASS COLLABORATION
  • Provide a notes-request board for students within the same authorized class.
  • Allow students to request a topic's notes and mark a request fulfilled.
  • Support resource sharing with suitable permissions.
  • In demo mode, clearly state that data is local or simulated and cannot be seen by other devices.
  • For real cross-device sharing, use a configured backend with authentication and authorization.
  • Prevent students from accessing private data belonging to other classes or institutions.
  1. ADMINISTRATION
  • Provide a college administration dashboard.
  • Manage departments, courses, semesters, divisions, subjects, academic calendar, and timetable.
  • Approve or revoke teacher access.
  • Manage student enrollment and joining codes.
  • Provide a basic audit trail for important administrative changes if the backend supports it.
  • Restrict every administrative action to authorized users from that institution.
  1. DATA MODEL AND SECURITY Design a sensible data model for colleges, profiles, enrollments, courses, classes, subjects, announcements, notes, assignments, task progress, timetable entries, calendar events, study sessions, and notes requests.
  • Include institution and class relationships wherever required.
  • Apply secure access policies at the database/backend layer.
  • Validate input on both client and server.
  • Use safe file handling and access-controlled file storage.
  • Never expose private credentials, student data, or secret API keys.
  • Do not use real student information in demo data.
  • Avoid collecting unnecessary personal information.
  1. IMPLEMENTATION QUALITY
  • Every visible button, form, filter, navigation item, and primary action must work.
  • Include loading, error, success, and empty states.
  • Add form validation and helpful error messages.
  • Make the interface usable on desktop and mobile.
  • Use reusable components and maintainable code.
  • Preserve existing working functionality when making changes.
  • Do not create fake analytics or misleading success messages.
  • Do not silently substitute nonfunctional controls for real features.
  1. TESTING Test the key user journeys: A. Student selects a demo college and views their dashboard. B. Student sees only relevant class announcements. C. Verified teacher creates an announcement for an authorized class. D. Teacher publishes notes associated with a topic. E. Teacher creates an assignment with a deadline. F. Student sees the assignment in the unified feed and deadline tracker. G. Student adds a study session and updates task progress. H. Administrator manages their own college's academic information. I. Unauthorized users cannot publish official notices or access another college's restricted data. J. Timetable and calendar entries display the correct dates. K. Refreshing the app does not lose persisted data when persistence is supported.

Fix errors found during testing. Report which tests actually passed and which could not be tested. Never claim a test passed without running it.

  1. DELIVERY Build the app in the current workspace. Generate all necessary source files and configuration examples. Run the app if the environment supports it. Give me:
  • The running preview or deployment instructions.
  • A clear project folder structure.
  • Setup and run commands.
  • Database schema and configuration instructions, if applicable.
  • A list of working features.
  • A list of simulated/demo-only features.
  • A list of incomplete features and limitations.
  • A simple explanation of how the main parts work.
  • Instructions for safely deploying the application.

IMPLEMENTATION ORDER Phase 1: Create the working application shell, responsive navigation, demo login, and role-based dashboards. Phase 2: Implement the unified announcement feed, teacher announcement creation, notes library, and assignment deadlines. Phase 3: Implement the student study planner, timetable, and academic calendar. Phase 4: Implement multi-college data separation, administrator controls, and real authentication/storage if supported. Phase 5: Test, fix errors, and document limitations.

Start by inspecting the current workspace and available capabilities. Then implement Phase 1 and the highest-priority features of Phase 2. Do not stop at a written plan. Build the application, run it, and tell me exactly how to test it.
